Walk away. Come back to the branch.

One coding agent in one terminal is easy to follow. Several are not. Botbench gives each task its own copy and branch, asks you only about what reaches outside it, and keeps a record of everything that ran.

Five steps, ending in a decision.

What you come back to is the last step: a branch, its checks and a review, waiting for Accept or Reject.

  1. You start a task or a run

    A task is a prompt and a repository. A run is a prompt or a spec file, which Claude Code turns into a plan of tasks. In a manual run, and in any run from a GitHub issue, nothing is built before you approve the plan.

  2. Each task gets a separate copy

    It is built in its own copy of your repository (a git worktree), on its own branch, such as botbench/your-mac/run-1/task-1.

  3. The agent works, and asks only when it matters

    Reading, searching and editing inside the copy never ask, in any mode. An action that reaches outside the copy waits for your answer: a push, sudo, a file outside the copy. A fully autonomous run refuses these instead of asking.

  4. Botbench commits and checks

    It runs the checks you set for the repository. If you chose a reviewer, it reads the change; with concerns, the builder makes a round of fixes and the checks and the review run again.

  5. You accept or reject

    You read the diff, the checks and the transcript. Accept keeps the branch, and opens a pull request if the run says so. Botbench never merges one.

Choose how much each run needs you.

A mode is about your decisions, not about which tools an agent has. The safety rules are the same in every mode.

A run started from a GitHub issue always waits for your approval of its plan and is never fully autonomous. The conditions for accepting without you are on Evidence.

Know the answer before the agent asks.

Check a command shows what any command would get in each mode, before an agent runs it. Permissions also lists what you chose to always allow, and every action that ran, newest first. The record is kept on your Mac and is only ever added to.

Commands you trust for a repository, such as npm test, can be allowed in advance in its settings.

Is it a sandbox?

Partly, and not a hard one.

The macOS sandbox confines the commands an agent runs: they cannot read your sign-ins, keys or Keychain, reach no network except hosts you allow for that repository, and can write only in the task’s copy and a temporary folder.

It is not a virtual machine or a container. A separate copy separates changes; it is not a security boundary. Claude Code itself runs outside the sandbox with your rights, and your repository’s setup and check commands can still read your home folder outside the protected places. Point Botbench only at repositories you trust.

Does my code leave my Mac?

Yes, as it does when you use the agents directly.

Each agent sends your prompts and the code it reads to its provider. Botbench does not change that, and sends little else. Without your choosing it: every 6 hours, one request to GitHub for Botbench’s latest release, with nothing about you in it, and your own gh and git reading other workbenches’ pull requests and branches. Only if you chose it: a pull request for a run, a notification to your phone, a claim on an issue.

Plans, transcripts, diffs, check results and approvals stay in a database on your Mac. Botbench listens on 127.0.0.1 only; do not put it on the public internet.
