Your team's coordination

Your agents. Their agents. One coordinated workflow.

Add a teammate who hands work to their own agents, and the two of you become the messengers. Botbench does the first steps about that today. The larger part is still to come, and this page says which is which.

Today

Two workbenches on one repository.

Each developer runs their own Botbench on their own Mac, behind its own login token. There are no accounts and no shared server; two workbenches share nothing but what they push to GitHub.

  1. Branches never clash Available

    Each workbench puts its name in its branches: botbench/<workbench>/run-N/task-M.

  2. You see each other's work Available

    The Work screen shows, read only, the other workbenches' open pull requests and pushed branches on the same remote, read with your own gh and git.

  3. You are warned before you overlap Available

    When another workbench already has a pull request open for the issue you attached, or has started on it. And when another workbench's open pull request changes the same files as your task.

  4. Only one of you takes an issue, if you choose Available

    A setting you turn on for a repository. A run from an issue that opens pull requests claims it as it starts; the remote takes only the first claim, and the other workbench's run stops and says who started first.

  5. You can check two changes together Available

    Botbench merges your ready task with a teammate's open pull request in a temporary copy and runs the repository's own checks on the merge, so you learn that two changes do not fit before either is merged. Nothing is pushed.

  6. You can ask each other directly, once paired Early

    Either of you, or your agent with your Send, can ask the other workbench a question about the repository you share. The other owner answers it, gives it to their Claude Code, or dismisses it.

Paired workbenches · Early

Every message is one its owner approved.

Pairing is off until you add a listener to Botbench's settings file. Then one owner makes an invite, the other pastes it, you compare fingerprints, and both confirm. The two workbenches then talk directly: no relay and no Botbench service.

A message that arrives is a card marked Outside text. It is not a command, it never runs anything, and it carries no file.

Its limits today. One pairing per installation, on one repository. Questions and answers only. Tested with two installations on one Mac over the loopback address, not across two Macs.

Where it is going

Planned, not in the code.

The coordination layer is meant to connect separately owned workbenches, so that your agents and a colleague's coordinate who does what, exchange the context each owner chose to share, and finish work together, with the people watching and steering instead of relaying every message. A message from another workbench will never be permission to run anything.

How much of a conversation between workbenches a person must approve is an open question, set out in the autonomy trade-off. Coding is where this starts. It is not meant to be where it ends, and nothing beyond coding is built.

Bring the agents you already use.
