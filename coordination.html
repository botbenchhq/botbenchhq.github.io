Your agents. Their agents. One coordinated workflow.

Two developers, each with their own agents, find out they took the same issue when the second pull request opens. With Botbench on both Macs, each workbench sees the other’s work on the repository you share, and tells you before then.

Each of you runs your own Botbench on your own Mac. There are no accounts and no shared server: the workbenches meet in the GitHub repository you both push to, read with your own gh and git.

What each workbench sees.

Two developers reach for the same issue, and then the same file. Botbench’s lines are its own; the names are examples.

Available today

Three warnings, in Botbench’s own words, with example names. Each needs both workbenches to push their branches or open pull requests on the same remote, with gh signed in on each Mac.

The same files

When another workbench’s open pull request changes the same files as your task, the task’s Review tab says so under the changed files:

office-mac’s open pull request #12 also changes calc.py, so the two may conflict when both are merged.
The same issue

Turn on issue claims for a repository ("claimIssues": true, off by default). A run from an issue that opens pull requests claims it as it starts; the remote takes only the first claim, and the later run stops:

studio-mac started on issue #42 at 14:14:07 UTC on 2026-11-25, before this workbench did (14:15:02 UTC on 2026-11-25), so this run stopped: when two workbenches start on one issue, the earliest claim goes ahead.

Before you start, Botbench also warns when another workbench already has a pull request open for the issue you attached.

Changes that must fit

On a task that is ready for review, choose Check together with a teammate’s open pull request. Botbench merges the two in a temporary copy, runs the repository’s own checks on the merge, pushes nothing, and shows the result as including another workbench’s code:

Passed together: Merged cleanly, and every check passed on the merge.

A pass proves only what your checks cover, and counts only while both branches stay at the commits it ran on.

Branches never clash
Each workbench puts its name in its branches: botbench/<workbench>/run-N/task-M.
You see each other’s work
The Work screen shows, read only, the other workbenches’ open pull requests and pushed branches on the same remote.
Nothing else is written
Apart from a claim, Botbench writes nothing to GitHub for this, and puts nothing another workbench wrote into a prompt to your agents.

Early

Ask the other workbench, once paired.

Either of you, or your agent with your Send, can ask the paired workbench a question about the repository you share. The other owner answers it, gives it to their Claude Code, or dismisses it. Every message that leaves is one its owner approved.

Pairing is off until you add a listener to Botbench’s settings file. Then one owner makes an invite, the other pastes it, you compare fingerprints, and both confirm. The two workbenches talk directly: no relay and no Botbench service. A message that arrives is a card marked Outside text: not a command, it never runs anything, and it carries no file.

Its limits today. One pairing per installation, on one repository. Questions and answers only. Tested with two installations on one Mac over the loopback address, not across two Macs.

Planned, not built.

The coordination layer is meant to connect separately owned workbenches, so that your agents and a colleague’s coordinate who does what and finish work together, with the people steering instead of relaying every message. None of the rows below is in the code. A message from another workbench will never be permission to run anything.
